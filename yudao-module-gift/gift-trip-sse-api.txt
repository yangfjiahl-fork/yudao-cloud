Gift 旅行规划 C 端接入 API
==========================

更新日期：2026-08-25

一、通用约定
------------

- API 前缀：`/app-api`。
- `conversationId`、`messageId` 及候选实体的 `id` 均按字符串保存，不能转为 JavaScript `number`。
- 发送消息是 POST SSE。请使用 `fetch + ReadableStream`，不要使用仅支持 GET 的 `EventSource`。
- SSE 每帧格式为：`data:{"code":0,"msg":"","data":{...}}\n\n`；业务事件读取 `data.event`。
- SSE 建立前的参数、鉴权或权限错误可能返回普通 JSON 错误；SSE 已建立后的执行错误会以 `event=error` 返回。

建议请求头：

    Content-Type: application/json
    Accept: text/event-stream
    Authorization: Bearer <member access token>
    tenant-id: <tenant id>

二、创建会话
------------

`POST /app-api/ai/chat/conversation/create`

请求体可为空。创建时已知省市区可传：

    {
      "provinceId":"330000",
      "cityId":"330100",
      "districtId":"330106"
    }

成功后返回单帧 SSE：

    data:{"code":0,"msg":"","data":{
      "event":"created",
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581777",
      "content":"告诉我目的地、出行日期和同行人数，我来帮你规划旅程。"
    }}

前端保存 `conversationId`，并将 `content` 作为第一条助手文本展示。

三、发送消息并接收流
----------------------

`POST /app-api/ai/chat/message/send-stream`

    {
      "conversationId":"1781604279872581776",
      "content":"10 月去杭州玩 3 天，两个人，喜欢美食和人文"
    }

用户发言由前端先乐观插入；本接口流只处理助手侧的 loading、追问和行程结果。

四、SSE 事件
------------

所有字段均位于外层响应的 `data` 内。

| 事件 | 关键字段 | 前端处理 |
| --- | --- | --- |
| `accepted` | `conversationId` | 创建本轮请求状态，开始 loading。 |
| `stage` | `stage=INTAKE|COMPOSER`、`content` | 更新 loading 文案；不写入聊天记录。 |
| `intake_completed` | `content`、`missingRequired` | 本轮需求已完成整理与校验；展示简短摘要，不写入聊天记录。 |
| `question` | `messageId`、`content`、`missingRequired`、`suggestions` | 插入正式助手消息，并展示可选胶囊；点击胶囊后发送下一轮消息。 |
| `assistant_start` | `stage=COMPOSER` | 创建临时的行程摘要/骨架区域。 |
| `assistant_delta` | `content`、`sequence` | 追加到临时摘要，实现逐字展示；不能单独成为聊天消息。 |
| `itinerary_day_started` | `sequence`、`item.day` | 已开始流式生成第 N 天；显示“正在规划第 N 天”，不创建日程卡。 |
| `itinerary_item` | `item`、`sequence` | 按 `item.day` 更新临时的单日预览；不能简单追加。 |
| `assistant_end` | - | 停止摘要光标，继续等待最终骨架。 |
| `itinerary_skeleton` | `messageId`、`content`、`itinerary` | 用完整骨架替换临时预览，插入正式助手行程消息，并发加载可见节点。 |
| `done` | - | 结束本轮 loading，清理临时请求状态。 |
| `error` | `content` | 显示错误并结束 loading；该分支后不会再有 `done`。 |

`stage` 只可能为：

- `INTAKE`：正在理解并补全出行需求。
- `COMPOSER`：正在生成行程骨架。

五、事件顺序
------------

信息不完整时：

    accepted -> stage(INTAKE) -> intake_completed -> question -> done

首次信息已齐、等待用户确认时：

    accepted -> stage(INTAKE) -> intake_completed -> question(missingRequired=[]) -> done

用户点击“直接生成行程”或明确要求生成后：

    accepted -> stage(INTAKE) -> intake_completed -> stage(COMPOSER) -> assistant_start
             -> (assistant_delta | itinerary_day_started | itinerary_item)*
             -> assistant_end -> itinerary_skeleton -> done

`assistant_delta`、`itinerary_day_started` 和 `itinerary_item` 的先后取决于流内容；前端不得依赖数量或固定顺序。`itinerary_day_started` 只表示已开始生成，最终以 `itinerary_item` 和 `itinerary_skeleton` 为准。

`question.suggestions` 最多 5 项，字段含义如下：

- `label`：胶囊显示文字。
- `content`：用户点击后，作为下一轮 `send-stream.content` 原样提交。

胶囊是辅助输入，不替代 `question.content` 中的关键追问。用户仍可自由输入；点击后按正常用户消息展示，不需要额外接口。

当 `missingRequired` 为空时，`question` 表示出行信息已经齐全，等待用户选择“直接生成行程”或继续补充；前端应正常展示该助手消息与胶囊，不能当作错误或空结果。

`question` 示例：

    {
      "event":"question",
      "stage":"INTAKE",
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581780",
      "content":"你的出行日期，或计划玩几天？",
      "missingRequired":["date_or_days"],
      "suggestions":[
        {"label":"玩 3 天","content":"计划玩3天"},
        {"label":"2 人出行","content":"总共2人出行"},
        {"label":"人均 ¥1,500","content":"人均预算1500元"}
      ]
    }

`itinerary_skeleton` 示例：

    {
      "event":"itinerary_skeleton",
      "stage":"COMPOSER",
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581790",
      "content":"杭州三日人文美食之旅",
      "missingRequired":[],
      "itinerary":{
        "version":1,
        "summary":"杭州三日人文美食之旅",
        "daily_itinerary":[
          {
            "day":1,
            "title":"初识杭州",
            "slots":[
              {"slot":"MORNING","label":"上午","skeleton":"城市核心区域慢游","status":"PENDING"},
              {"slot":"LUNCH","label":"午餐","skeleton":"安排本地风味午餐","status":"PENDING"},
              {"slot":"AFTERNOON","label":"下午","skeleton":"人文景点与街区活动","status":"PENDING"},
              {"slot":"DINNER","label":"晚餐","skeleton":"晚餐与休息安排","status":"PENDING"},
              {"slot":"EVENING","label":"晚上","skeleton":"轻松夜间活动","status":"PENDING"},
              {"slot":"ACCOMMODATION","label":"住宿","skeleton":"住宿候选待补充","status":"PENDING"}
            ]
          }
        ],
        "transport":{
          "arrival":{"status":"PENDING","skeleton":"抵达交通待确认"},
          "departure":{"status":"PENDING","skeleton":"返程交通待确认"}
        },
        "booking_actions":[],
        "warnings":[],
        "citation_ids":[]
      }
    }

六、并行补充行程节点
--------------------

收到 `itinerary_skeleton` 后，前端可先展示文字骨架，再对当前可见卡片并行请求补充信息。MVP 中每个半天节点最多返回 2 个地点；它们是同一段行程的推荐组合，不是要求用户二选一。

`POST /app-api/ai/chat/message/itinerary/slot/resolve`

日内节点：

    {
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581790",
      "day":1,
      "slot":"MORNING"
    }

首尾交通：

    {
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581790",
      "day":0,
      "slot":"ARRIVAL"
    }

支持的节点：

- 日内：`MORNING`、`LUNCH`、`AFTERNOON`、`DINNER`、`EVENING`、`ACCOMMODATION`。
- 交通：`ARRIVAL`、`DEPARTURE`，`day` 必须为 `0`。

该接口只能请求当前行程骨架。建议并发上限为 4，离屏节点延迟加载。

成功响应：

    {
      "code":0,
      "msg":"",
      "data":{
        "messageId":"1781604279872581790",
        "day":1,
        "slot":"MORNING",
        "status":"RESOLVED",
        "detail":"已获取 2 个景点候选",
        "candidates":[
          {
            "id":"178...",
            "type":"POI",
            "name":"杭州西湖风景名胜区",
            "provider":"gaode",
            "externalId":"B0...",
            "metadata":{"address":"...","imageUrl":"..."}
          }
        ],
        "citationIds":["178..."]
      }
    }

节点状态：

- `PENDING`：暂无可展示的补充结果。保留骨架并显示“待确认”。
- `RESOLVED`：有可展示候选；日内景点节点最多 2 个，按返回顺序展示为同一时段的推荐地点。候选不表示已预订或最终确定。

收到响应后，按 `(messageId, day, slot)` 覆盖对应卡片的 `status`、`detail`、`candidates`、`citationIds`。图片只在 `candidate.metadata.imageUrl` 非空时加载，失败时显示占位图。

七、修改已生成行程
------------------

首次信息齐全后，前端应等待用户点击“直接生成行程”或用自然语言明确要求生成。生成过计划后，修改仍使用“发送消息”接口，前端只传自然语言，无需也不能传 Agent、行程版本或节点操作：

    {
      "conversationId":"1781604279872581776",
      "content":"第 2 天下午改成轻松的室内活动，晚餐保留"
    }

有效修改会生成一个新版本，返回事件序列与首次生成骨架完全一致；最终会收到新的 `itinerary_skeleton`、新的 `messageId` 和递增的 `itinerary.version`。

前端处理：

1. 将本轮用户修改作为普通用户消息展示。
2. 收到新的 `itinerary_skeleton` 后，用其整体替换“当前行程”视图；`itinerary.version` 仅用于展示或标记历史版本，不作为下一次请求参数。
3. 使用新的 `messageId` 重新加载可见节点；不要复用旧行程的节点请求和结果。
4. 历史聊天中旧行程仍按旧消息和旧版本展示，不需要被替换。

八、历史消息恢复
----------------

`GET /app-api/ai/chat/message/list-by-conversation-id?conversationId=...`

正常聊天消息按 `content` 显示。助手行程消息会带可选 `itinerary` 字段：

    {
      "id":"1781604279872581790",
      "type":"ASSISTANT",
      "content":"杭州三日人文美食之旅",
      "itinerary":{"version":2,"summary":"杭州三日人文美食之旅","daily_itinerary":[]}
    }

有 `itinerary` 时按行程卡片渲染；没有时按普通文本消息渲染。页面恢复历史时不需要重放旧 SSE，也不应再次请求旧行程节点。

九、流读取要点
--------------

1. 用 `response.body.getReader()` 和 `TextDecoder` 的 stream 模式读取 UTF-8。
2. 缓存未完成文本，按空行切分 SSE 帧；兼容 `\n\n` 和 `\r\n\r\n`。
3. 一个网络 chunk 不等于一帧 SSE：一帧可能跨多个 chunk，多帧也可能合并在同一 chunk。
4. 解析每帧时先判断外层 `code`，再分发 `data.event`。
5. 页面卸载或用户取消时，用 `AbortController` 中止 fetch，并清理本轮 loading。
