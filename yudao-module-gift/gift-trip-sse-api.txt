Gift 旅行规划 C 端 SSE API 接入说明
====================================

更新日期：2026-08-24（以当前后端实现为准）

一、通用约定
------------

- API 前缀：`/app-api`。
- 创建会话和发送消息均返回 `Content-Type: text/event-stream`。
- 每一帧格式为 `data:{CommonResult JSON}\n\n`。业务事件在 `data.event`，不是 SSE 协议的 `event:` 行。
- `conversationId`、`messageId` 由后端序列化为 JSON 字符串；前端必须以 `string` 保存，不能转为 JavaScript `number`。
- 这是 POST SSE，请使用 `fetch + ReadableStream` 读取响应；浏览器原生 `EventSource` 仅支持 GET，不能直接使用。
- 一帧正常业务数据的外层固定为 `{"code":0,"msg":"","data":{...}}`。前端先判断 `code`，再读取 `data.event`。
- 客户端主动断开时，不保证会收到 `done`。应在取消请求时主动关闭 loading。

二、接口
----------

1. 创建会话

`POST /app-api/ai/chat/conversation/create`

请求体可为空；也可传入已知行政区划：

    {
      "provinceId": "330000",
      "cityId": "330100",
      "districtId": "330106"
    }

当前只返回一帧 `created`，其中 `content` 是本地随机引导语，不是模型输出：

    data:{"code":0,"msg":"","data":{"event":"created","conversationId":"1781604279872581776","messageId":"1781604279872581777","content":"告诉我目的地、出行日期和同行人数，我来帮你规划旅程。"}}

拿到 `conversationId` 后保存会话，并将 `content` 作为第一条助手文本消息展示。

2. 发送消息并接收流

`POST /app-api/ai/chat/message/send-stream`

    {
      "conversationId":"1781604279872581776",
      "content":"10 月去杭州玩 3 天，两个人，喜欢美食和人文"
    }

请求前会同步校验会话归属。会话不存在、没有权限或请求体校验失败时，接口可能直接返回普通错误响应，而不是包含 `data.event=error` 的 SSE 帧。

建议请求头：

    Content-Type: application/json
    Accept: text/event-stream
    Authorization: Bearer <member access token>
    tenant-id: <tenant id>

鉴权和租户头沿用现有 C 端请求封装。

三、响应字段
------------

所有字段均位于 `data`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `event` | string | 必填。事件名，见下文。 |
| `stage` | string | 可选。仅为 `INTAKE`、`RESEARCH`、`COMPOSER` 之一。 |
| `conversationId` | string | 除创建会话的错误场景外均有。 |
| `messageId` | string | 仅 `created`、`question`、`itinerary` 有。对应已持久化的聊天消息。 |
| `content` | string | 可选。状态提示、追问、摘要增量或最终摘要。不可将状态提示当作事实。 |
| `sequence` | integer | 仅 `assistant_delta`、`itinerary_item` 有；从 1 开始，在同一次 Composer 流中递增，两个事件共享同一序列。 |
| `itemType` | string | `itinerary_item` 为 `daily_itinerary`；`tool_result` 为工具类型。 |
| `item` | object | `itinerary_item` 为一天的预览卡片；`tool_result` 为 ToolPlan。 |
| `itinerary` | object | 仅最终 `itinerary` 有；完整且已持久化的行程。 |
| `missingRequired` | string[] | `question` 为缺失字段；最终 `itinerary` 固定为空数组。 |

四、当前实际事件
----------------

1. `created`

仅创建会话接口返回。前端建立会话并展示 `content`。

2. `accepted`

发送消息接口的第一帧，表示该次请求已进入 SSE 执行链。前端可开始 loading；不要创建助手气泡。

    {"event":"accepted","conversationId":"1781604279872581776"}

3. `stage`

服务端进入状态机节点时发送。`content` 是可展示但不稳定的进度提示文案，前端可更新 loading 状态，不应存为聊天消息。

    {"event":"stage","stage":"INTAKE","content":"正在提取本轮出行需求…"}

当前可能的阶段：

- `INTAKE`：流式调用需求抽取角色，合并 JSON patch 并由确定性代码校验状态。
- `RESEARCH`：执行受控的酒店候选、景点与适用的当前天气查询，并读取未过期事实。模型不决定工具、供应商或查询参数。
- `COMPOSER`：流式调用行程生成角色，解析其严格 JSON 输出。

4. `tool_result`

一个确定性检索节点完成后发送。它不是模型 Token，也不是正式聊天消息；前端可用 `content` 更新检索进度，并按 `item.type` / `item.status` 渲染结果状态。当前每轮最多 3 条。

    {
      "event":"tool_result",
      "stage":"RESEARCH",
      "content":"已获取 3 个景点候选",
      "itemType":"SCENIC_SPOT_QUERY",
      "item":{"type":"SCENIC_SPOT_QUERY","status":"EXECUTED","entityId":"178...","detail":"已获取 3 个景点候选"}
    }

`status` 仅可能为：`EXECUTED`（本轮调用完成）、`CACHED`（使用未过期事实）、`SKIPPED`（当前能力不适用，例如未来日期不能用当前天气替代预报）、`FAILED`（外部服务暂不可用，Composer 会保持待确认）。酒店候选当前为固定占位数据，图片地址为空，不代表价格、库存或可预订性。

4. `question`

最小必填信息不足时发送。它是一条已写入聊天记录的正式助手消息：用 `messageId` 创建或确认气泡，直接展示 `content`。

    {
      "event":"question",
      "stage":"INTAKE",
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581780",
      "content":"你的出行日期，或计划玩几天？",
      "missingRequired":["date_or_days"]
    }

当前缺失字段只会是：

- `destination`：目的地。
- `date_or_days`：完整日期范围或出行天数至少提供一个。

注意：Intake 的模型输出是内部 JSON，不会以逐字 `assistant_delta` 返回；因此追问只会在 Intake 完成校验后以一帧 `question` 到达。

5. `assistant_start`

Composer 已开始生成最终方案。此事件当前没有 `content` 和 `sequence`。前端创建一个“行程摘要生成中”的临时区域即可。

6. `assistant_delta`

Composer 严格 JSON 的 `summary` 字段增量。按接收顺序或 `sequence` 将 `content` 追加到同一临时摘要区域，才能逐字显示；不要把每个 delta 保存成单独气泡。

    {
      "event":"assistant_delta",
      "stage":"COMPOSER",
      "content":"杭州三日",
      "sequence":1
    }

`assistant_delta` 只代表摘要，不代表整份 JSON，也不包含当天活动、交通或预约字段。

7. `itinerary_item`

Composer 的 `daily_itinerary` 数组中某个对象已经闭合、能被解析时立即发送。前端可据此渐进渲染或更新“第 N 天”卡片。

    {
      "event":"itinerary_item",
      "stage":"COMPOSER",
      "sequence":7,
      "itemType":"daily_itinerary",
      "item":{
        "day":1,
        "title":"西湖与老城区",
        "activities":["上午游览西湖","午餐地点待确认"]
      }
    }

此事件是预览：最终必须以 `itinerary.daily_itinerary` 整体替换或校正卡片，不能把预览与最终数组简单追加。

8. `assistant_end`

Composer 输出已完成并通过后端行程校验、持久化；此事件无 `content`、`messageId`、`sequence`。前端停止摘要的流式光标，但不要关闭整轮 loading，仍需等待最终 `itinerary`。

9. `itinerary`

完整行程已保存，并已创建一条正式助手聊天消息。`content` 为 `summary`，`messageId` 对应该摘要消息；用 `itinerary` 替换临时摘要和全部日程预览。

    {
      "event":"itinerary",
      "stage":"COMPOSER",
      "conversationId":"1781604279872581776",
      "messageId":"1781604279872581790",
      "content":"杭州三日人文美食之旅",
      "itinerary":{
        "summary":"杭州三日人文美食之旅",
        "daily_itinerary":[{"day":1,"title":"西湖","activities":["..."]}],
        "transport":["实时班次待确认"],
        "booking_actions":["预约规则待确认"],
        "warnings":["天气和营业信息待确认"],
        "citation_ids":[]
      },
      "missingRequired":[]
    }

10. `done`

本轮正常结束。关闭 loading、清除临时状态。`done` 本身不携带内容或 sequence。

11. `error`

仅代表 SSE 已建立后的异步执行失败，例如模型调用或行程 JSON 校验失败。展示 `content`，关闭 loading；此分支后不会再发送 `done`。

    {"event":"error","conversationId":"1781604279872581776","content":"暂时无法生成旅行方案，请稍后重试。"}

五、事件顺序
------------

信息不足：

    accepted -> stage(INTAKE) -> question -> done

生成行程：

    accepted -> stage(INTAKE) -> stage(RESEARCH) -> stage(COMPOSER)
             -> tool_result* -> assistant_start -> (assistant_delta | itinerary_item)*
             -> assistant_end -> itinerary -> done

- `assistant_delta` 和 `itinerary_item` 的先后取决于 Composer JSON 的实际输出，不能假设所有 delta 都先于所有卡片。
- 前端不能依赖增量数量；应以 `itinerary` 作为最终成功结果。
- 不会发送泛化的 `progress` 事件。`tool_result` 是确定性工具节点的唯一进度结果；模型慢调用仍通过 `assistant_delta` 展示。
- 最终 `daily_itinerary[].activities[]` 兼容字符串，也可为实体引用对象：`{"entityId":"...","type":"POI|HOTEL|RESTAURANT","title":"...","description":"..."}`。前端按对象的 `entityId` 关联候选卡；后端会拒绝不存在的实体编号。

六、流读取要求
--------------

1. 使用 `response.body.getReader()` 与 `TextDecoder` 的 stream 模式读取 UTF-8 数据。
2. 缓存未完成文本，按空行分割 SSE 帧；同时兼容 `\n\n` 与 `\r\n\r\n`。
3. 一个网络 chunk 不等于一帧 SSE：一帧可能跨多个 chunk，多帧也可能合并到同一个 chunk。
4. 对一帧中的 `data:` 行取出 JSON 后再 `JSON.parse`；先处理外层 `code`，再分发 `data.event`。
5. 页面卸载或用户取消时使用 `AbortController` 中止 fetch，并清理 loading。

七、推荐前端状态处理
--------------------

1. 收到 `accepted`：创建本轮 request 状态并显示 loading。
2. 收到 `stage`：更新 loading 文案；不落聊天记录。
3. 收到 `tool_result`：更新本轮检索进度或候选卡片；不落聊天记录，也不可据 `FAILED` 推断事实。
4. 收到 `question`：插入正式助手消息，结束本轮。
5. 收到 `assistant_start`：创建内存中的临时 summary/card 状态。
6. 收到 `assistant_delta`：追加 `content` 到临时 summary。
7. 收到 `itinerary_item`：按 `item.day` upsert 临时日程卡；不要重复插入。
8. 收到 `itinerary`：以完整 `itinerary` 替换临时 summary 与日程卡，并将 `messageId` 对应的 `content` 作为正式聊天消息。
9. 收到 `done` 或 `error`：结束 loading，清理本轮临时 request 状态。

八、持久化与重连限制
--------------------

- `gift_trip_plan` 是跨轮 TripState 和缺失字段的唯一状态来源。
- `gift_trip_run` 记录 Intake、Research、Composer 的输入/输出快照、模型、token、耗时和失败信息。
- `gift_trip_itinerary` 保存最终完整 JSON；`itinerary_item` 不单独持久化。
- `gift_trip_itinerary.message_id` 逻辑关联 `ai_chat_message.id`；一条最终行程对应一条助手消息。
- `GET /app-api/ai/chat/message/list-by-conversation-id?conversationId=...` 是唯一的 C 端历史恢复接口。它先读取消息，再批量读取关联行程；行程助手消息会额外携带可选字段 `itinerary`，前端可直接恢复完整卡片。例如：

      {
        "id":"1781604279872581790",
        "type":"ASSISTANT",
        "content":"杭州三日人文美食之旅",
        "itinerary":{"summary":"杭州三日人文美食之旅","daily_itinerary":[]}
      }

- 没有 `itinerary` 的消息按普通文本渲染。`gift_trip_run` 只用于运行审计，不参与 C 端消息恢复。

九、Chat Role 配置
-------------------

- `trip.agent.intakeRoleId`：需求抽取角色，仅后端内部调用。
- `trip.agent.composerRoleId`：行程生成角色，同时用于创建可见会话。
- 两个角色必须是当前租户启用的 MEMBER Chat Role，并关联可用模型。
- Chat Role ID 不会出现在 C 端请求或 SSE 响应中。
